Feishu OpenPlatform Server SDK for Python
商店应用 ClientAssertion 认证
中文
The Feishu Open Platform provides server-side APIs for messaging, contacts,
approval, sheets, Base, and many other product capabilities. This SDK wraps the
repeated platform work around API calls, including token management, request
signing, encryption/decryption, event dispatching, and typed request/response
models.

Installation
pip install lark-oapi
Python 3.8 or later is required.
Basic Usage
import lark_oapi as lark
from lark_oapi.api.im.v1 import *
client = lark.Client.builder() \
.app_id("cli_xxx") \
.app_secret("your_app_secret") \
.build()
request = CreateMessageRequest.builder() \
.receive_id_type("chat_id") \
.request_body(CreateMessageRequestBody.builder()
.receive_id("oc_xxx")
.msg_type("text")
.content("{\"text\":\"hello world\"}")
.build()) \
.build()
response = client.im.v1.message.create(request)
ClientAssertion Keyless Mode
For self-built apps and eligible ISV apps that use an external signing service, the SDK can fetch
tenant tokens with client_assertion instead of app_secret. The SDK does not
generate, parse, sign, or store JWT private keys; your provider supplies the
final assertion string.
import os
import lark_oapi as lark
from lark_oapi.core.client_assertion import ClientAssertionToken
class EnvClientAssertionProvider:
def retrieve_token(self, aud: str) -> ClientAssertionToken:
return ClientAssertionToken(os.environ["LARK_CLIENT_ASSERTION"])
client = lark.Client.builder() \
.app_id(os.environ["LARK_APP_ID"]) \
.client_assertion_provider(EnvClientAssertionProvider()) \
.build()
If you use a custom OpenAPI domain, also configure oauth_base_url(...) so the
SDK can derive the OAuth audience correctly. Eligible ISV apps also set
app_type(lark.AppType.ISV) and pass tenant_key for tenant API calls.
Keyless mode does not support AppAccessToken-only APIs.
One-Click App Registration
lark_oapi.register_app creates an app through the OAuth device flow. It
returns a verification URL in on_qr_code; render the URL as a QR code or show
it as a link for the user to open in Feishu/Lark.
import lark_oapi as lark
def on_qr_code(info):
print(info["url"])
result = lark.register_app(
on_qr_code=on_qr_code,
app_preset={
"avatar": [
"https://example.com/a.png",
"https://example.com/b.webp",
],
"name": "{user}'s app",
"desc": "Created by the business platform",
},
)
print(result["client_id"])
Custom scopes/events/callbacks and updating an existing app
When creating an app, use addons to incrementally request scopes, event subscriptions,
and callbacks on top of the platform base template. They are pre-filled into the
confirm page shown after the user scans the QR code, and take effect once the user
confirms:
result = lark.register_app(
on_qr_code=on_qr_code,
addons={
"scopes": {
"tenant": ["im:message:send_as_bot"],
"user": ["calendar:calendar:read"],
},
"events": {"items": {"tenant": ["im.message.receive_v1"]}},
"callbacks": {"items": ["card.action.trigger"]},
},
create_only=True,
)
lark.register_app(
on_qr_code=on_qr_code,
app_id="cli_xxx",
addons={"scopes": {"tenant": ["drive:drive.metadata:readonly"]}},
)
Notes:
addons is additive only: items are merged on top of the base template; base permissions can never be removed.
addons.preset picks the base template: omitted or True keeps the default base template, while False switches to the minimal base template so the final config only contains what addons declares. With "preset": False, an addons without any incremental item is also valid.
Only the 5 public config types are supported: tenant/user scopes, tenant/user events, and callbacks. Sensitive config such as event request URLs, security.*, or encrypt keys cannot travel through addons.
The SDK validates the shape, not the item names; names unknown to the platform catalog are ignored by the confirm page.
For a real manual E2E run without mocked registration responses:
python3 samples/registration/app_preset_live_e2e.py --open

Legacy Channel Module
lark_oapi.channel is the legacy Channel entry point kept for compatibility
during the migration window. New Channel features ship in
lark-channel-sdk with the
lark_channel import path; critical fixes for existing lark_oapi.channel
users are evaluated for backport until 2027-06-02.
lark-channel-sdk can be installed alongside lark-oapi. Its
SecurityConfig
defaults to compatibility mode so migrated bots can roll out with audit mode
before strict enforcement. See the
migration guide
for the full checklist.
pip install lark-channel-sdk
from lark_channel import FeishuChannel
Existing legacy import example:
import asyncio
import os
from lark_oapi.channel import FeishuChannel
channel = FeishuChannel(
app_id=os.environ["LARK_APP_ID"],
app_secret=os.environ["LARK_APP_SECRET"],
)
async def on_message(msg):
await channel.send(
msg.chat_id,
{"text": f"echo: {msg.content_text}"},
)
channel.on("message", on_message)
asyncio.run(channel.connect())

Webhook authentication
When no EncryptKey is configured and a nonempty VerificationToken is explicitly supplied, the SDK validates the token before invoking event or callback handlers: top-level token for v1 and header.token for v2. Missing, null, empty, non-string, or mismatched tokens are rejected. Challenge responses also validate explicitly configured verification tokens.
Leaving both credentials empty retains the previous behavior. Encrypted events retain existing decryption and signature checks, and WebSocket clients continue using trusted internal dispatch.
Rollback: reverting this change restores the validation gap for explicitly configured VerificationTokens. Keep independent webhook authentication in place before rolling back.
Runtime webhook credentials
Register a combined provider while building the handler:
handler = (lark.EventDispatcherHandler.builder("", "")
.webhook_credentials_provider(credential_store.get_webhook_credentials)
.build())
The provider is called once per HTTP webhook (events, callbacks, and challenge), before decryption and validation. It is not called while building the handler or by trusted WebSocket dispatch. The returned pair overrides static credentials for that request only; the next request sees updates. The example store method returns a lark.WebhookCredentials value and reads the complete pair atomically from a thread-safe local cache. Providers must return promptly, with caller-owned timeouts for any I/O. Empty strings retain legacy empty-configuration behavior. Invalid results and exceptions reject the request without static fallback, and original exception details are not logged or returned. Provider registration is initialization-only. Monitor acquisition latency and failures in the provider. Remove the provider registration to return to static credentials.
WebSocket connection host and handshake headers
domain controls HTTP endpoint discovery. The optional connection host replaces only the WebSocket URL host[:port], preserving scheme, path and query. Default DNS and TLS/SNI follow the resulting hostname; existing custom transport settings still apply. Domains below are placeholders.
client = lark.ws.Client(
os.environ["APP_ID"], os.environ["APP_SECRET"],
domain="https://bootstrap.example.com",
connection_host="websocket.example.com:443",
connection_headers={"X-Route": "events"},
event_handler=event_handler,
)
Handshake headers are copied at initialization and for each handshake, including reconnects, and are never forwarded to endpoint discovery. Omitting both settings preserves existing behavior. Host, Connection, Upgrade and Sec-WebSocket-* cannot be overridden through headers. Basic host checks reject empty values, schemes/paths and query parameters; other address and header settings are passed to the underlying libraries without additional SDK format checks. These basic host and reserved-header checks run before network I/O (Start returns an error in Go; construction/build throws in other SDKs). Use trusted developer configuration, not headers/hosts supplied by an end-user request.
