The Smartsheet Model Context Protocol (MCP) server provides a way to leverage Smartsheet’s public API via AI clients, allowing you to interact with your data using natural language. The MCP server's underlying tools (operations) interact with your Smartsheet data (with your permission) to respond to your prompts. The following sections describe the key tools available to your AI client once connected to the Smartsheet MCP server.
Required plan: Business, Enterprise, or Advanced Work Management
To execute any tool, your AI client requires specific OAuth access scopes. Each tool lists its Access scopes below its name.
For starters, explore the discovery and navigation tools.
Tokens are the basic units that AI language models use to process text. They're chunks of text that can be individual words, parts of words, or even punctuation marks. Both your input and the AI's responses are measured in tokens. This matters because:
Models have maximum token limits (context windows)
Processing speed decreases with increasing token count
The tools are subject to Smartsheet API rate limiting and standard limitations.
Discovery and navigation
search
Access scopes: READ_SHEETS
The search tool is a discovery tool that lets you search across all accessible Smartsheet assets to find resources by name or content.
This tool is particularly useful as a starting point when you need to find an asset ID before using other Smartsheet tools like browse_workspace, browse_folder, or get_sheet_summary.
Basic Parameters
query (required): The search term to look for. Use specific terms like "Q4 Budget" for better results. You can use double-quotes for exact matches (e.g., "Q4 Budget 2024").
scopes (optional): Narrow your search to specific asset types. Available scopes include:
sheetNames — Search in sheet names
reportNames — Search in report names
sightNames — Search in dashboard names
folderNames — Search in folder names
workspaceNames — Search in workspace names
cellData — Search within cell contents
comments — Search in comments
attachments — Search in file attachments
summaryFields — Search in summary fields
templateNames — Search in template names
modified_since (optional): Filter results by modification date using ISO 8601 timestamp format to find resources changed after a specific date.
Key Features
Fuzzy Matching: Supports approximate matching, so you don't need exact names.
Results Context: Returns asset names, types, parent folder/workspace context, match excerpts, and favorite indicators.
Maximum Results: Returns up to 100 results (no pagination available).
Wide Coverage: Can search across sheets, reports, dashboards, folders, workspaces, and more in one call.
Limitations
Eventually consistent (new items may take a few minutes to appear in search results).
First-time API users may experience a 24-hour data provisioning delay.
Returns maximum 100 results with no pagination options.
Use Cases
Discover assets: Find sheets, reports, or dashboards when you don't know exact IDs or locations.
Locate by content: Search for specific text within sheets or comments.
Browse by modification date: Find recently updated assets.
Find attachments: Locate files attached to sheets or discussions.
Workspaces and folders
browse_workspace
Access scopes: READ_SHEETS
The browse_workspace tool lets you explore all the contents of a workspace, discovering the top-level sheets, reports, dashboards, and folders it contains. Here's the breakdown:
Basic Parameters
workspace_id (required): The ID of the workspace to browse. Obtain this from list_workspaces or the search tool.
asset_types (optional): Filter results by specific resource types:
folders — Nested folders
sheets — Individual sheets
reports — Reports
sights — Dashboards
templates - Templates
If not specified, returns all asset types.
max_item (optional): Control page size (1–1000 items per page; defaults to 100).
last_key (optional): Token for pagination. Use the last_key from a previous response to fetch the next page of results.
Key Features
Top-Level Only: Returns direct children of the workspace (not recursively nested contents within folders).
Token-Based Pagination: Supports pagination via last_key for workspaces with more than 100 items.
Server-Side Filtering: Filter by asset type during the request, not after retrieving results.
Asset Information: Returns names, IDs, types, creation/modification dates, and favorite status for each asset.
Limitations
Returns only top-level workspace contents (doesn't drill into nested folder structures).
Maximum 1000 items per page.
Requires a valid workspace ID.
Use Cases
Discover workspace structure: See all sheets, reports, and dashboards at the workspace root level.
Find assets by type: List only sheets or only dashboards in a workspace.
Navigate hierarchically: Get folder IDs to use with browse_folder for deeper exploration.
Inventory assets: Audit what's in a workspace without searching.
browse_folder
Access scopes: READ_SHEETS
The browse_folder tool navigates and explores the contents of a specific folder within Smartsheet. It retrieves all direct children of a folder—including nested folders, sheets, reports, and dashboards—making it essential for hierarchical folder navigation. This tool helps users discover and access assets organized within folder structures without needing to know exact resource IDs in advance.
Basic Parameters
folder_id - The unique identifier of the folder to browse (positive integer; obtain from search results, browse_workspace results, or parent folder responses).
asset_types - (Optional) Filter results by resource type; acceptable values are "folders", "sheets", "reports", "sights" (dashboards) or "templates". Pass as an array to filter for multiple types, or omit to return all asset types.
last_key - (Optional) Pagination token from a previous response used to fetch the next page of results; leave empty for the first page.
max_item - (Optional) Number of items to return per page, ranging from 1 to 1000; defaults to 100.
Key Features
Hierarchical Navigation - Returns only direct children of the specified folder, allowing step-by-step exploration of nested folder structures.
Asset Type Filtering - Efficiently narrow results to specific resource types (folders, sheets, reports, dashboards) to surface only the resources you need.
Pagination Support - Handles large folder contents through token-based pagination; use the last_key parameter to retrieve subsequent pages when more than 100 items exist.
Complete Asset Details - Provides metadata for each child resource, including IDs, names, permalinks, and ownership information needed for downstream operations.
Limitations
Returns only direct children, not a recursive tree of all nested contents.
Maximum of 1000 items returned per page; folders with more than 100 children require pagination.
Does not include folder content counts or summary statistics for performance reasons.
Use Cases
Folder Content Exploration - Browse the contents of a folder to discover sheets, reports, dashboards, and subfolders without knowing their exact IDs.
Asset Filtering - Filter results to show only sheets or only reports within a folder for focused navigation.
Hierarchical Traversal - Use folder_id values returned from browse_folder results to navigate deeper into nested folder structures.
Pagination Through Large Folders - Systematically retrieve all contents of folders with more than 100 items using token-based pagination.
Asset Inventory - Build a complete map of folder structure and contents for administrative or archival purposes.
list_workspaces
Access scopes: READ_SHEETS
Retrieves a list of workspaces from Smartsheet with pagination support. This tool is essential for discovering and managing all workspaces within a Smartsheet account, allowing you to browse the organization's workspace structure without nested content exploration.
Best Practices
Use pagination parameters (last_key and max_item) when working with large numbers of workspaces to avoid overwhelming API responses.
Store workspace IDs after retrieval for use in subsequent operations like creating sheets, folders, or browsing workspace contents.
Cache workspace lists locally if you perform frequent lookups to reduce API calls.
Set max_item appropriately based on your needs; smaller values reduce response size while larger values (up to 1000) retrieve more results in a single call.
Basic Parameters
last_key (optional string): Token used for server-side pagination to retrieve the next page of workspaces. Leave empty for the first request.
max_item (optional integer, default 100): Maximum number of workspace items to return per page. Range: 1–100.
Key Features
Pagination support: Retrieve workspaces in manageable batches using last_key for cursor-based pagination across large workspace lists.
Flexible page sizing: Control result set size with max_item to balance between API efficiency and result count.
Workspace discovery: Get a comprehensive list of all accessible workspaces in your Smartsheet account with a single call.
Token-based navigation: Use returned last_key values to traverse large result sets without offset limitations.
Limitations
Maximum 1000 items returned per request (enforced by max_item parameter cap).
Returns top-level workspace list only; does not include workspace contents.
Requires valid Smartsheet authentication; cannot list workspaces from other accounts.
No filtering by workspace type or attributes available; returns all accessible workspaces.
Use Cases
Initial workspace discovery: Retrieve all workspaces to present users with a selection menu or dashboard.
Workspace enumeration: Build a complete inventory of workspaces for auditing or reporting purposes.
Paginated browsing: Handle accounts with hundreds of workspaces by iterating through pages with pagination tokens.
Workspace ID lookup: Obtain workspace IDs needed as prerequisites for creating sheets, folders, or accessing workspace contents.
create_workspace
Access scopes: ADMIN_WORKSPACES
create_workspace creates a new workspace with a name. A workspace is a top-level container that organizes sheets, reports, dashboards, and folders within your Smartsheet environment. This tool enables you to establish a new organizational structure for your projects and data management.
Best Practices
Use descriptive and meaningful workspace names that reflect the purpose or team associated with the workspace.
Consider naming conventions that align with your organization's standards for consistency across multiple workspaces.
Basic Parameters
name - The name to assign to the new workspace.
Key Features
Workspace creation - Establishes a new top-level container for organizing Smartsheet assets.
Foundation for hierarchy - Serves as the parent container for folders, sheets, reports, and dashboards.
Limitations
Workspace names that are empty or whitespace-only are rejected at validation time.
Workspace names that are longer than 50 characters are rejected at validation time.
Use Cases
Team-based organization - Create separate workspaces for different teams or departments to maintain clear separation of work and resources.
Project management - Establish a workspace dedicated to a specific project to house all related sheets, reports, and tracking documents.
Department structuring - Set up workspaces for different functional areas such as Finance, Marketing, or Operations to organize departmental assets centrally.
create_folder
Access scopes: ADMIN_WORKSPACES
create_folder creates a new folder within a specified workspace or parent folder, enabling hierarchical folder organization within Smartsheet.
Best Practices
Establish a clear naming convention before creating folders to maintain consistency across workspaces and nested folder structures.
Use the browse_workspace tool or the browse_folder tool to verify the container ID and type before calling this tool.
Verify you have ADMIN permissions on the target container before attempting to create folders.
Basic Parameters
parent_id: The ID of the workspace or parent folder in which to create the new folder. Obtain this value from the list_workspaces tool, the browse_workspace tool, or the browse_folder tool. This parameter is required.
parent_type: The type of container receiving the new folder. Accepted values are WORKSPACE and FOLDER. This parameter is required.
folder: A folder object containing the name property, which specifies the folder's display name. The name must be non-empty and unique within the parent container. This parameter is required.
Key Features
Unified container support: Creates folders in either a workspace or a parent folder through a single tool, replacing two separate tools.
Hierarchical organization: Supports building multi-level folder structures by targeting either a top-level workspace or an existing folder as the parent container.
Unique naming enforcement: Enforces unique folder names within each parent container to maintain organization clarity.
Folder details returned: Returns the created folder's ID and permalink for reference and use in further operations.
Deep nesting support: Smartsheet supports deep folder nesting, allowing you to create complex organizational hierarchies.
Limitations
User must have ADMIN permissions on the target container (workspace or folder) to create folders.
Folder names must be unique within the parent container.
Folder names that are empty or whitespace-only are rejected at validation time.
Folder names that are longer than 50 characters are rejected at validation time.
Use Cases
Project organization: Create separate folders for different projects or departments directly within a workspace or nested inside an existing folder.
Asset categorization: Organize sheets by team, function, or business unit at any level of the folder hierarchy.
Workspace setup: Establish the initial top-level folder structure when building out a new workspace.
Client management: Build hierarchical folder structures to separate different clients and their associated sheets, reports, and dashboards.
Template libraries: Organize template sheets in nested folders by category or purpose for easy discovery and reuse.
Archive structure: Create dated or categorized sub-folders within an archive folder to maintain historical records in an organized manner.
Solutions
create_workspace_assets
Access scopes: ADMIN_WORKSPACES, ADMIN_SHEETS, CREATE_SHEETS, WRITE_SHEETS, CREATE_SIGHTS
Toolset: ai_solutions
The create_workspace_assets tool is an AI agent that builds comprehensive, end-to-end Smartsheet solutions from natural language descriptions. It can create any combination of workspaces, sheets, dashboards, workflows, reports, forms, portfolios, projects, and blueprints in a single call. The caller can describe what to build explicitly or describe a problem, and the agent designs and generates an appropriate solution autonomously. This tool is optimized for multi-asset, integrated solutions and is not intended for creating a single asset in isolation.
This tool is unavailable for the Microsoft 365 Copilot Connector (the Copilot Studio connector for Copilot Chat)
Basic Parameters
message (required): Natural language description of what to create or the problem to solve. Maximum 1000 characters.
Key Features
End-to-end solution generation: Creates a complete, integrated Smartsheet solution in one call, handling workspace setup through individual asset creation automatically.
Multi-asset output: Returns summaries for all created assets — sheets, dashboards, automations, reports, forms, portfolios, projects, and blueprints — each with their ID and permalink.
Problem-driven design: Accepts either an explicit specification or a problem description, and the AI determines the appropriate solution architecture.
Progress reporting: Reports progress as work proceeds during multi-step creation operations.
Limitations
Creation time varies with complexity; typical completion is 1–2 minutes, and complex multi-asset solutions may take longer.
The AI makes best-effort interpretations of ambiguous requirements; vague descriptions may produce incomplete or unexpected results.
Not intended for creating a single asset — use individual tools for single-asset operations.
In rare cases, a needed asset type may not be created; check the returned summary and fall back to individual creation tools as needed.
Use Cases
Project tracking workspace: Build a complete project tracking solution with intake sheets, status dashboards, automated notifications, and summary reports from a single description.
Problem-driven setup: Describe a business problem (for example, "I need to track vendor onboarding") and let the AI design and provision the full Smartsheet solution.
Portfolio initialization: Stand up a portfolio with project templates, a project list sheet, and portfolio-level dashboards in one request.
Data collection pipeline: Create an end-to-end solution that includes a form for data collection, a backing sheet, automated row routing, and an executive dashboard.
Cross-functional workspace: Generate a workspace spanning multiple teams with sheets, shared reports, and role-appropriate dashboards from a natural language brief.
Sheets
get_sheet_path
Access scopes: READ_SHEETS
get_sheet_path gets the full hierarchical path of a sheet within the Smartsheet workspace, including a UNIX-style path and a direct permalink, without loading the sheet itself.
Best Practices
The following items are best practices for using the get_sheet_path tool:
Provide at least one of sheet_id or url. The tool requires at least one value to locate the sheet.
If providing both sheet_id and url, ensure they refer to the same sheet. Mismatched values result in an error.
Use this tool instead of the get_sheet_summary tool when only the sheet's location or permalink is needed, since it avoids loading sheet content.
Basic Parameters
The get_sheet_path tool has the following parameters:
sheet_id: The numeric ID of the target sheet. The sheet_id parameter defaults to null.
url: The URL of the target sheet. The url parameter defaults to null.
Key Features
The get_sheet_path tool has the following key features:
Hierarchical path: Returns the full folder structure from the workspace root to the sheet as a UNIX-style path, making it easy to understand where the sheet resides.
Direct permalink: Returns a shareable permalink to the sheet without requiring the sheet's content to be loaded.
Lightweight lookup: Retrieves location metadata only, without loading sheet rows, columns, or other content.
Flexible input: Accepts either a sheet ID or a sheet URL as input, accommodating different starting points.
Limitations
The get_sheet_path tool has the following limitations:
At least one of sheet_id or url must be provided. If both are provided, they must refer to the same sheet.
Requires workspace-level access to the sheet. If the user does not have this access, the API returns a 404 error.
The returned path reflects only the folder structure up to the sheet and does not include any sheet content.
Use Cases
The following items describe use cases for the get_sheet_path tool:
Locating a sheet: Determine where a sheet lives within the workspace hierarchy without loading the sheet itself.
Generating a shareable link: Retrieve a direct permalink to a sheet for sharing with collaborators.
Workspace navigation: Quickly identify the folder path of a sheet as part of a broader workspace audit or inventory task.
Lightweight sheet lookup: Use in place of the get_sheet_summary tool when only location metadata is needed, reducing unnecessary data retrieval.
get_sheet_summary
Access scopes: READ_SHEETS
Retrieves sheet data with optional multi-column filtering, sorting, and column selection. This tool lets you analyze, summarize, or work with Smartsheet data flexibly by narrowing results to exactly what you need.
Best Practices
Call get_columns first when using filters, sorting, or column selection parameters to get exact case-sensitive column names—guessing column names results in validation errors.
Provide either a Smartsheet URL or a sheet_id, but not both (if both are provided, they must match).
Apply filters and column selection to minimize data transfer and improve performance.
Use filters to narrow results down to specific records.
Remember that column names are case-sensitive.
Basic Parameters
url (optional) — Smartsheet URL for the sheet.
sheet_id (optional) — Numeric ID of the sheet.
filters (optional) — Array of column filters with AND logic (requires column name, operator, and value).
sorting (optional) — Array of sort criteria specifying column name and direction (ASCENDING or DESCENDING).
columns (optional) — List of specific column names to fetch (narrows returned data).
Key Features
Multi-column filtering — Apply multiple filters using AND logic with operators like EQUAL, NOT_EQUAL, LESS_THAN, GREATER_THAN, and comparison variants.
Flexible sorting — Sort results by one or more columns in ascending or descending order.
Column selection — Specify only the columns you need to reduce payload size.
Data exploration — Returns available columns metadata for subsequent use when called without filters.
High-capacity data access — Handles large sheets with intelligent sampling when data exceeds token limits.
Limitations
Data is limited to approximately 8,000 tokens, so very large sheets may return sampled rows.
Filters use AND logic only (no OR conditions).
Column names are case-sensitive; validation errors occur if names don't match exactly.
Sorting falls back to Modified Date DESC or primary column ASC if not explicitly specified.
Must provide either a URL or sheet ID (at least one is required)
Use Cases
Data analysis and reporting — Summarize sheet contents, extract key metrics, or prepare data for external reporting.
Filtered data retrieval — Pull only rows matching specific criteria (e.g., all tasks with status "In Progress").
Sorted data views — Organize results by priority, date, or other columns for quick review.
Column-focused queries — Fetch specific columns to reduce noise and focus on relevant information.
Pre-deletion verification — Review sheet data before using destructive operations like row deletion.
Dynamic dashboarding — Feed filtered, sorted data into dashboards or external applications.
get_sheet_version
Access scopes: READ_SHEETS
The get_sheet_version tool retrieves the current version number of a Smartsheet without loading the entire sheet. Version numbers increment on any modification to the sheet, making this a lightweight change detection mechanism.
Best Practices
Use version polling to determine if a full sheet refresh is needed before calling resource-intensive tools like get_sheet_summary.
Store the version number locally and compare it on subsequent calls to track changes efficiently.
Combine with other tools: call get_sheet_version first to check if the sheet has changed since your last retrieval.
Provide either a Smartsheet URL or a sheet_id, but not both (if both are provided, they must match).
Basic Parameters
sheet_id: The numeric identifier for the sheet (optional if URL is provided).
url: The Smartsheet URL for the sheet (optional if sheet_id is provided).
Key Features
Minimal Payload: Returns only the version number without any row, column, or metadata content.
Change Detection: Version increments automatically on cell value changes, comments, row modifications, attachments, and formatting updates.
Monotonic Versioning: Version numbers are strictly increasing integers that start at zero.
Limitations
Returns only a version number with no historical data or change details.
Cannot retrieve previous version numbers or version history.
Does not indicate what changed, only that a change occurred.
Use Cases
Caching Strategy: Implement efficient caching by storing the version number and re-fetching full data only when the version changes.
Lightweight Monitoring: Continuously monitor sheets for modifications without the overhead of loading entire datasets.
Conditional Updates: Determine whether other tools need to be called based on whether the sheet version has incremented.
find_in_sheet
Access scopes: READ_SHEETS
The find_in_sheet tool searches for text within a specific Smartsheet sheet. It returns matching cells with row and column IDs, display values, and character offsets for each match. It supports case-sensitive search, column-scoped filtering, formula-based filtering, sorting, and pagination.
Best Practices
Restrict the search to specific columns using the columns parameter when you know where the target data lives, to improve performance and reduce noise.
Use the filter parameter with a formula (for example, =OR([Status]@row = "Active")) to pre-filter rows before the search term is applied, narrowing results to relevant data.
Use pagination (limit and offset) when working with large sheets to manage result set size.
Basic Parameters
sheet_id — The integer ID of the target sheet to search within.
request.term — The search term to look for, between 1 and 250 characters.
request.caseSensitive — Boolean flag indicating whether the search is case-sensitive. It defaults to false.
request.columns — An optional array of column IDs that restricts the search to only those columns.
request.filter — An optional formula string (must begin with =) applied to filter rows before searching.
request.sort — An optional array of up to three sort criteria, each specifying a column name and sort direction (ASC or DESC).
limit — The maximum number of results to return per page. Accepts values from 1 to 20,000. It dßefaults to 100.
offset — The zero-based pagination offset for retrieving subsequent pages of results.
Key Features
Cell-level results — Returns matches at the individual cell level, including the row ID, column ID, display value, and character offset of the match within the cell.
Column scoping — Restricts the search to a specified subset of columns, reducing irrelevant matches.
Formula filtering — Applies a Smartsheet formula as a pre-search row filter, enabling logic-based scoping before the term is evaluated.
Case sensitivity control — Toggles case-sensitive matching on or off to suit the precision requirements of the search.
Multi-column sorting — Sorts the result set by up to three columns, each with an independent direction.
Pagination support — Supports high-volume result sets with configurable page size (up to 20,000 results) and offset-based paging.
Use Cases
Data auditing — Locate all cells containing a specific value, such as a vendor name or status code, across an entire sheet for review or correction.
Targeted column search — Scope a search to one or more specific columns to find entries like duplicate email addresses or incorrectly-formatted dates without scanning irrelevant data.
Conditional data lookup — Combine a formula filter with a search term to find matching cells only within rows that meet a business condition, such as only active projects or open tickets.
create_sheet
The create_sheet tool creates a new sheet within a specified Smartsheet folder or workspace.
The tool supports two creation modes:
Building a blank sheet from scratch with fully custom column definitions
Instantiating a sheet from an existing template
The create_sheet tool serves as the primary entry point for adding new structured data grids to an organization's Smartsheet environment.
Access scopes: CREATE_SHEETS
Best Practices
The following items are best practices for using the create_sheet tool:
Always designate exactly one column as the primary column (using primary: true) when creating a blank sheet, and ensure that column is of type TEXT_NUMBER.
When creating from a template, use the include parameter to selectively copy only the elements you need (such as data, attachments, or rules) to avoid unnecessary duplication.
Verify the target container ID and type before calling this tool, using the browse_folder or browse_workspace tool to confirm the destination exists and that you have edit permissions on it.
Choose column types carefully at creation time, as restructuring columns after rows have been added is more disruptive.
Basic Parameters
The create_sheet tool has the following parameters:
container_id — The integer ID of the folder or workspace in which to create the sheet.
container_type — The type of container, either FOLDER or WORKSPACE.
sheet — The sheet definition object. Pass a CreateSheet object (with a name and columns array) for a blank sheet, or a CreateSheetFromTemplate object (with a name and fromId) when creating from a template.
include — An optional list of elements to copy from the template when using CreateSheetFromTemplate. Valid values are attachments, cellLinks, data, discussions, filters, forms, ruleRecipients, and rules. This parameter is ignored when creating a blank sheet.
Key Features
The create_sheet tool has the following key features:
Blank sheet creation — Accepts a fully custom column schema, allowing you to define column titles, types, options, formulas, formatting, and system column types (such as AUTO_NUMBER, CREATED_DATE, or MODIFIED_BY) at creation time.
Template-based creation — Creates a new sheet pre-populated with the structure (and optionally the content) of any accessible template by referencing its ID via fromId.
Selective template element copying — When creating from a template, the include parameter lets you choose exactly which elements (data, attachments, discussions, filters, forms, rules, etc.) to copy into the new sheet.
Flexible container targeting — Supports placing the new sheet in either a folder or a workspace by specifying the container_type and container_id.
Project and Gantt configuration — Accepts optional ganttEnabled, dependenciesEnabled, resourceManagementEnabled, and projectSettings fields to configure the sheet as a project sheet at creation time.
Rich column typing — Supports a full range of column types including TEXT_NUMBER, DATE, DATETIME, CHECKBOX, CONTACT_LIST, MULTI_CONTACT_LIST, PICKLIST, MULTI_PICKLIST, PREDECESSOR, DURATION, and ABSTRACT_DATETIME.
Limitations
The create_sheet tool has the following limitations:
The sheet name must be unique within the target container; duplicate names in the same folder or workspace are not allowed.
The user must have edit permissions on the parent container (folder or workspace).
When creating from a template, the template must be accessible to the authenticated user.
Exactly one column must be designated as the primary column when creating a blank sheet, and it must be of type TEXT_NUMBER.
Column titles must remain unique within the sheet; duplicates cause the operation to fail.
Column titles are limited to 50 characters.
Use cases
The following items describe use cases for the create_sheet tool:
Standardized project intake — Create a new project tracking sheet from a pre-approved template, copying filters and rules so every project sheet starts with consistent structure and automation.
Dynamic report scaffolding — Programmatically generate a blank sheet with a specific set of columns to serve as a data destination for an automated reporting workflow.
Team onboarding — Spin up a personal task sheet for each new team member inside a shared workspace, using a template that includes standard columns and pre-filled data rows.
Gantt project initialization — Create a sheet with ganttEnabled and dependenciesEnabled set to true and pre-tagged GANTT_START_DATE, GANTT_END_DATE, and GANTT_PREDECESSOR columns to immediately support dependency-driven scheduling.
Audit trail sheets — Create a sheet that includes CREATED_BY, CREATED_DATE, MODIFIED_BY, and MODIFIED_DATE system columns to automatically capture row-level audit information.
Columns
get_columns
Access scopes: READ_SHEETS
The get_columns tool retrieves detailed column metadata from a Smartsheet, allowing you to discover all available columns in a sheet along with their properties and types.
Basic Parameters
sheet_id (optional): The numeric identifier of the sheet to retrieve columns from.
url (optional): A valid Smartsheet URL to retrieve columns from (you must provide at least one of sheet_id or url).
Key Features
Complete metadata discovery: Returns all columns in a sheet with their IDs, names, types, and properties.
Column type information: Identifies column types such as TEXT_NUMBER, DATE, PICKLIST, CHECKBOX, CONTACT_LIST, and more.
Preparation for other operations: Essential to run before using filters, sorting, or column selection in other tools since column names are case-sensitive.
Property inspection: Shows column-specific properties like options for picklists, auto-number formats, and system column designations.
Limitations
This tool returns metadata only and does not retrieve row data itself.
Use Cases
Discovering available columns: Explore the complete structure of a sheet before writing filters or retrieving data.
Validating column names: Confirm exact case-sensitive column names before using them in filters, sorting, or column selection parameters.
Planning data operations: Understand column types and properties to design appropriate filtering and sorting strategies.
Column reference: Obtain column IDs needed for other operations like updating columns, deleting columns, or retrieving cell history.
add_columns
Access scopes: ADMIN_SHEETS
The add_columns tool adds one or more new columns to a specified Smartsheet with customizable properties such as type, position, formula, and validation rules.
Best Practices
Use a common index value as the starting point when creating multiple columns at once; subsequent columns automatically increment their index positions.
Ensure column titles are unique within the sheet to avoid naming conflicts.
Define appropriate column types upfront to enable proper data validation and formatting.
Use formulas for computed columns to maintain data consistency across your sheet.
Basic Parameters
sheet_id - The numeric identifier of the sheet where columns is to be added.
columns - An array of column objects, each containing required and optional properties that define the column structure.
title - The display name for the column, which must be unique within the sheet. The maximum length is 50 characters.
type - The column type that determines how data is stored and displayed (e.g., TEXT_NUMBER, DATE, CONTACT_LIST, PICKLIST, CHECKBOX, DURATION, MULTI_CONTACT_LIST, MULTI_PICKLIST, DATETIME, ABSTRACT_DATETIME, PREDECESSOR).
index - A zero-based position indicating where the column is to be placed in the sheet layout.
description - An optional text field for documenting the column's purpose.
formula - An optional expression for computed columns that automatically calculate values.
hidden - An optional boolean to hide the column from the default view.
locked - An optional boolean to prevent editing of the column.
format - An optional display format string for customizing how data appears.
options - An array of predefined values for PICKLIST columns.
primary - An optional boolean flag to designate this as the primary column (only TEXT_NUMBER columns can be primary).
symbol - An optional symbol set name for enhanced visual representation.
width - An optional pixel value to set the column width.
validation - An optional boolean to enable validation rules for the column.
autoNumberFormat - An optional configuration object for auto-numbering systems with prefix, suffix, fill padding, and starting number.
contactOptions - An optional array of contact configurations for CONTACT_LIST columns, specifying name and email.

The attach_url tool has the following parameters:

attachment.attachmentSubType — An optional sub-classification of the attachment, used only with GOOGLE_DRIVE or EGNYTE attachment types. Valid values are DOCUMENT, SPREADSHEET, PRESENTATION, PDF, DRAWING, and FOLDER. The FOLDER sub-type applies only to EGNYTE; all other sub-types apply to GOOGLE_DRIVE. Google Drive sub-type classification — An optional attachmentSubType parameter enables further classification of Google Drive items by file type (document, spreadsheet, presentation, PDF, drawing) or folder type for Egnyte.

The attach_url tool has the following limitations:

create_report
The create_report tool creates a new Smartsheet report that aggregates data from one or more source sheets or from all of the sheets in one or more workspaces. The create_report tool supports custom column definitions, filters, grouping, sorting, and summarizing criteria, and can produce either a row report or a sheet summary report.
Access scopes: READ_SHEETS
Best Practices
The following items are best practices for using the create_report tool:
Verify that all column title values exactly match the corresponding column titles in the source sheets, as matching is case-sensitive and must be precise.
Ensure all column index values are unique and zero-based across the full column definition list.
For row reports, designate exactly one column with primary=true using type=TEXT_NUMBER.
For sheet summary reports, designate exactly one column with sheetNameColumn=true using type=TEXT_NUMBER.
When grouping criteria are defined, be aware that the primary column moves to index 0 on first render in the app, which may affect expected column ordering.
Use the the get_report tool after creation to confirm the report structure and data before sharing or embedding the report in dashboards.
Basic Parameters
The create_report tool has the following parameters:
name — The report name, between 1 and 50 characters.
destination — The destination folder or workspace where the report is created, specified as an object with a destinationId (the numeric folder or workspace ID) and a destinationType (either "folder" or "workspace").
scope — A list of 1 to 100 source sheets or workspaces to aggregate, each specified with an assetId and an assetType of either "sheet" or "workspace".
columns — A list of 1 to 400 column definitions, each with a zero-based index, a type, and additional identifying fields depending on the column kind (regular, system, primary, or sheet name column). Optional per-column fields include hidden, width, primary, sheetNameColumn, systemColumnType, and title.
is_summary_report — A boolean that controls whether the report is a sheet summary report (true) or a row report (false). The is_summary_report parameter defaults to false.
report_definition — An optional object containing filters, groupingCriteria, sortingCriteria, and summarizingCriteria to shape the report's data presentation.
Refer to the POST /2.0/reports API operation documentation for details on creating a report and specifying the report definition.
Key Features
The create_report tool has the following key features:
Row and summary report types — Supports both row reports, which aggregate individual rows from source sheets, and sheet summary reports, which aggregate sheet summary fields.
Multi-source scoping — Accepts up to 100 source sheets (specified explicitly or as part of workspaces) as input, enabling cross-sheet and cross-workspace data aggregation in a single report.
Flexible column definitions — Supports regular columns (matched by type and title), system columns (matched by type and system column type), primary columns, and sheet name columns, with optional hidden and width settings.
Filter expressions — Supports nested filter expressions up to 3 levels deep using AND/OR operators and a wide range of filter operators covering equality, comparisons, date ranges, blank checks, and multi-value matching.
Grouping criteria — Allows columns to be used as grouping criteria with configurable sort direction and expand/collapse state.
Sorting criteria — Supports multi-column sorting with ASCENDING or DESCENDING direction per column.
Summarizing criteria — Supports column-level aggregations using SUM, AVG, MIN, MAX, COUNT, FIRST, and LAST.
Limitations
The create_report tool has the following limitations:
Report names are limited to 50 characters.
A maximum of 400 columns may be defined per report.
The scope is limited to 100 sheets.
Filter expressions support a maximum nesting depth of 3 levels.
Use Cases
The following items describe use cases for the create_report tool:
Cross-sheet status rollup — Aggregate task status columns from multiple project sheets into a single report to give stakeholders a unified view of progress across all projects.
Department-wide resource tracking — Scope a report to an entire workspace to consolidate resource allocation rows from every sheet in a department's workspace.
Filtered executive summary — Create a row report with filter criteria that surfaces only high-priority or overdue items from across dozens of source sheets.
Grouped pipeline view — Define grouping criteria on a status or owner column to organize aggregated rows into collapsible sections for easier review.
Summarized financial rollup — Use summarizing criteria with SUM or AVG aggregations on numeric columns to produce totals and averages across source sheets.
Sheet summary dashboard feed — Create a sheet summary report (is_summary_report=true) to pull sheet-level summary fields together, useful for high-level KPI dashboards.
Sorted delivery schedule — Apply sorting criteria on a date column so that aggregated rows from multiple sheets appear in chronological order across the full report.

create_workflow
Access scopes: WRITE_SHEETS
Toolset: automations
create_workflow creates a new workflow on a sheet using human-readable names for columns, recipients, and other references. The workflow is defined as a typed tree specifying a trigger and a chain of actions or conditions.
Best Practices
The following items are best practices for using the create_workflow tool:
Use the get_workflows tool on an existing sheet to study the tree structure before composing a new workflow from scratch.
Verify that all referenced column titles, recipient emails, and document mapping names exist on the sheet before calling — unknown names are rejected by the API without creating anything.
Use {} for notificationCustomizationJson on EMAIL_RECIPIENT, UPDATE_REQUEST, and APPROVAL actions unless explicit customization is needed.
Basic Parameters
The create_workflow tool has the following parameters:
sheet_id (required): The ID of the sheet the workflow attaches to.
name (required): Display name for the workflow (up to 255 characters).
root_node (required): The workflow definition as a typed tree. The root has type: "ROOT_NODE" and contains a trigger and a childNode. All type discriminants are UPPER_SNAKE_CASE. Columns are referenced by title (columnTitle); people are referenced by email address. The ID field in recipient objects is always a string.
frequency (optional): How often the workflow runs once triggered. The frequency parameter defaults to RIGHT_AWAY (run immediately when the trigger fires).
enabled (optional): Whether the workflow is active immediately after creation. The enabled parameter defaults to true.
Key Features
The create_workflow tool has the following key features:
Human-readable references: Columns, recipients, and document mappings are specified by name rather than numeric ID, making workflows easier to compose and read.
Schema-validated tree: The root_node structure is validated before the API call; errors report the exact field path and permitted values for precise correction.
Immediate activation: Workflows are enabled by default upon creation; set enabled: false to create a workflow in a disabled state.
Limitations
The create_workflow tool has the following limitations:
All referenced column titles and email addresses must already exist on the sheet — the tool does not create missing resources.
Recipient emails must belong to Smartsheet users; assign-people emails must have an existing contact record.
Column title matching is case-sensitive.
Use Cases
The following items describe use cases for the create_workflow tool:
Automated notifications: Create a workflow that sends an email alert when a row's status column changes to a specific value.
Approval routing: Build an approval workflow triggered when a new row is added, sending an update request to a designated reviewer.
Scheduled reminders: Set up a time-based workflow that sends reminders at a defined frequency when a due-date condition is met.
Row automation: Automatically move or copy rows to another sheet when specific criteria are satisfied.
update_workflow
Access scopes: WRITE_SHEETS
Toolset: automations
The update_workflow tool updates a Smartsheet workflow by ID, fully replacing its definition using human-readable names. It overwrites the stored workflow tree with exactly the tree sent — anything omitted from root_node is removed from the workflow. Updating a workflow also invalidates any in-flight approval actions: pending approval emails stop being actionable.
(⚠️ destructive, irreversible)
Best Practices
The following items are best practices for using the update_workflow tool:
Call the get_workflows tool first to read the current definition, then modify it and send the COMPLETE tree back — never send a partial tree.
Omit enabled to preserve the workflow's current enabled/disabled state; only pass it to deliberately toggle that state.
Pass expected_version (from a previous update_workflow, enable_workflow, or disable_workflow response) to guard against concurrent edits; on a 409 conflict, re-read the workflow and retry with the fresh definition.
Reference columns by title and people by email; use UPPER_SNAKE_CASE for all type discriminants, exactly as in the create_workflow tool.
Do not include node id fields in root_node — the tree schema rejects them; node identity is regenerated on every edit.
Basic Parameters
The update_workflow tool has the following parameters:
workflow_id (required, string) — The ID of the workflow to update, as shown in Smartsheet.
sheet_id (required, integer) — The current sheet ID of the workflow. Must match the sheet the workflow already lives on — workflows cannot be moved to another sheet.
name (required, string) — The workflow display name to store. Up to 255 characters; may be empty.
root_node (required) — The complete replacement workflow tree using the by-names contract: {type: 'ROOT_NODE', trigger: {type: <TRIGGER_TYPE>, ...}, childNode: {type: <NODE_TYPE>, ...}}. Uses the same schema as the create_workflow tool. The stored definition becomes exactly this tree.
frequency (required) — How often the workflow runs once triggered. Must always be supplied on update; there is no default.
enabled (boolean, optional) — Whether the workflow is enabled. Omit to keep the current enabled/disabled state; pass true or false only to deliberately change it.
expected_version (integer, optional) — Optimistic-concurrency guard. The version from a previous update_workflow, enable_workflow, or disable_workflow response. If the workflow was edited by someone else since that version, the update fails with 409 and makes no changes. Omit for an unconditional update.
Key Features
The update_workflow tool has the following key features:
Full replacement semantics — The stored workflow definition becomes exactly the root_node tree sent; any node omitted is removed, making this a complete overwrite rather than a patch.
Human-readable names — Columns are referenced by title and recipients by email address, avoiding the need to look up internal IDs.
Optimistic concurrency control — The optional expected_version parameter detects concurrent edits and fails safely with 409, enabling read-modify-write patterns without data loss.
Enabled/disabled state preservation — Omitting enabled keeps the workflow's current state; an edit alone never inadvertently re-enables a disabled workflow.
Pre-flight tree validation — Tree-structure violations (invalid condition counts, missing child nodes, etc.) are caught and the offending path is reported before anything is sent to the backend.
Limitations
The update_workflow tool has the following limitations:
Full replace, not a patch: the workflow becomes exactly what is sent; any node omitted from root_node is removed.
sheet_id must be the workflow's current sheet — workflows cannot be moved to another sheet via update.
Updating a workflow invalidates its in-flight approval actions: pending approval emails stop being actionable.
The caller must have permission to edit the workflow's sheet.
Condition nodes must carry 1–20 conditions AND a childNode; IF_ELSE nodes require at least one condition branch; ELSE nodes require a childNode — violations are rejected with the offending path.
Node id fields must not be included in root_node — the schema rejects them.
Use Cases
The following items describe use cases for the update_workflow tool:
Modifying trigger or action configuration — Read the current workflow, adjust a trigger type or notification recipient, and write the full updated tree back.
Restructuring a workflow tree — Add, remove, or reorder condition branches and action nodes by sending a revised complete tree.
Renaming a workflow — Update the name field while passing the rest of the definition unchanged.

Pre-compute or extract all data values before calling this tool, since it does not perform any sheet queries.
Match the number of entries in each dataset's data array to the number of entries in labels to ensure a well-formed chart.
After the tool returns, always render the chart yourself using the labels from result.labelInfo.labels and the datasets from result.dataSetInfo.dataSets.
Basic Parameters
The create_chart_from_data tool has the following parameters:
chart_type: The type of chart to render. Accepted values are bar, line, pie, and stacked_bar.
datasets: An array of dataset objects. Each object has a data property (an array of numbers) and an optional label property for the series name.
labels: Category labels used on the x-axis for bar and line charts, or as segment labels for pie charts.
title: The chart title.
data_format: How to format data values displayed in the chart. Accepted values are number, currency, and percent. The data_format parameter defaults to number.
Key Features
The create_chart_from_data tool has the following key features:
Pre-computed data input: Accepts data you have already computed or extracted, giving you full control over what is charted without relying on a sheet query.
Multiple chart types: Supports bar, line, pie, and stacked_bar chart types to cover a range of visualization needs.
Multi-series support: Accepts multiple dataset objects in a single call, enabling side-by-side or layered series on the same chart.
Flexible data formatting: Formats displayed values as plain numbers, currency, or percentages via the data_format parameter.
Structured chart definition output: Returns a JSON chart definition containing labels and datasets that you use to render the chart as an artifact or inline visualization.
Limitations
The create_chart_from_data tool has the following limitations:
Does not query any Smartsheet sheet data; all values must be provided by the caller.
Cannot be refined using the refine_chart tool, as there is no backing conversation.
Cannot be added to a dashboard via the add_charts_to_dashboard tool, since it has no conversation backing.
Only supports the four chart types explicitly listed (bar, line, pie, stacked_bar); other chart types are not available.
Does not validate that dataset lengths match the number of labels, so mismatches must be avoided by the caller.
Use Cases
The following items describe use cases for the create_chart_from_data tool:
Visualizing externally sourced data: Charting data that originates outside Smartsheet, such as values from a CSV export, a database query, or a manual calculation.
Displaying aggregated metrics: Rendering summary statistics or KPIs that have already been computed, without needing to re-query a sheet.
Multi-series comparisons: Presenting multiple data series side by side — for example, comparing actual versus budgeted figures across several months.
Percentage and currency breakdowns: Displaying financial distributions or completion rates using the currency or percent data formats for cleaner presentation.
Custom chart construction: Building a precisely defined chart when the automatic AI-driven interpretation of the create_chart_from_prompt tool would not produce the exact structure needed.
refine_chart
Access scopes: READ_SHEETS
The refine_chart tool retrieves suggested follow-up refinements for an existing chart within an active conversation. It does not itself modify or update the chart — it returns a list of suggested next steps that can be applied by making a subsequent call to the create_chart_from_prompt tool.
Best Practices
The following items are best practices for using the refine_chart tool:
Use the create_chart_from_prompt tool before calling refine_chart to establish a valid conversation and obtain the required conversation_id and message_id.
To apply a chosen refinement, call the create_chart_from_prompt tool with the same conversation_id, the previous_message_id, and the refinement's prompt.
Basic Parameters
The refine_chart tool has the following parameters:
conversation_id — The conversation ID returned from the create_chart_from_prompt tool. This is required.
message_id — The message ID of the chart or metric answer to refine. This is required, and the message must be an answer (chart or metric), not a question.
count — The number of refinement suggestions to return. The count parameter defaults to 5, with a minimum of 1 and a maximum of 10.
Key Features
The refine_chart tool has the following key features:
Suggestion-based refinement — Returns a set of suggested refinements, each with a title, prompt, chart type, and type, giving users structured options for improving their chart.
Conversation continuity — Operates within an existing conversation started by the create_chart_from_prompt tool, preserving context across chart iterations.
Configurable suggestion count — Allows the caller to control how many refinement suggestions are returned, up to a maximum of 10.
Non-destructive operation — Does not alter the existing chart in any way; changes are only applied when a refinement prompt is passed to the create_chart_from_prompt tool.
Limitations
The refine_chart tool has the following limitations:
Requires an active conversation established by the create_chart_from_prompt tool; it cannot be used independently or with charts created via the create_chart_from_data tool.
Returns suggestions only — applying a refinement requires a separate follow-up call to the create_chart_from_prompt tool.
The message_id must reference an answer message (a chart or metric); question messages are not valid targets.
Charts created via create_chart_from_data cannot be refined using this tool, as they have no backing conversation.
Use Cases
The following items describe use cases for the refine_chart tool:
Iterative chart improvement — After generating an initial chart with the create_chart_from_prompt tool, use refine_chart to surface actionable next steps for improving the visualization.
Guided user experience — Present refinement suggestions to a user so they can select a direction for updating their chart without needing to write a new prompt from scratch.
Chart type exploration — Use returned chartType values in suggestions to help users discover alternative chart types that may better represent their data.
Multi-chart conversation management — In conversations that produce multiple charts or metrics, use refine_chart with a specific message_id to target refinements at a particular chart.

add_charts_to_dashboard
Access scopes: CREATE_SIGHTS
The add_charts_to_dashboard tool adds one or more previously created charts to a Smartsheet dashboard as new widgets in a single request. Each chart must have been created via the create_chart_from_prompt tool or refined via the refine_chart tool before it can be added. The tool returns a dashboardPermalink that links directly to the dashboard, and one result per chart, in the order the charts were supplied.
This tool is unavailable for the Microsoft 365 Copilot Connector (the Copilot Studio connector for Copilot Chat)
Best Practices
The following items are best practices for using the add_charts_to_dashboard tool:
Pass every chart destined for the same dashboard in one call, even when there is only one chart.
Don't add charts to the same dashboard with several calls in parallel. Each call places its widgets independently, so parallel calls can leave widgets overlapping.
For more than 10 charts, make consecutive calls and wait for each call to finish before starting the next one.
Verify that the target dashboard ID is correct before calling this tool, using the list_dashboards tool or the get_dashboard tool if needed.
Check each entry in results. A successful call doesn't mean every chart was added, so tell the user which charts were added and which weren't.
Only retry entries whose reason is NOT_ATTEMPTED, because those charts were never sent. Any other reason may already have created the widget, so retrying risks a duplicate.
Surface the returned dashboardPermalink to the user as a "View on dashboard" link so they can immediately see the result.
Basic Parameters
The add_charts_to_dashboard tool has the following parameters:
dashboard_id — An integer representing the ID of the dashboard where the chart widgets are placed.
charts — An array of 1 to 10 charts to add, in the order they should appear. Each chart has the following properties:
conversationId — A string representing the conversation ID returned from the chart creation or refinement response.
messageId — A string representing the message ID of the specific chart response to add.
messageType — A string representing the message type from the chart creation or refinement response (messages[].messageType). The value must be v2/ChartMessage.
Key Features
The add_charts_to_dashboard tool has the following key features:
Multiple charts in one call — Adds up to 10 charts to a dashboard in one request, placing them one after another so they don't overlap.
Per-chart results — Returns one entry per chart, in request order. Each entry has a type of SUCCEEDED or FAILED. A failed entry includes a reason, such as NOT_FOUND, UNAUTHORIZED, or NOT_ATTEMPTED.
Conversation-based workflow — Ties directly into the conversation flow started by the create_chart_from_prompt tool, using the conversationId and messageId from that flow to identify exactly which result to publish.
Dashboard permalink — Returns a dashboardPermalink, giving immediate access to the live dashboard view.
Widget metadata — Returns a chartId, version, and widgetId for each added chart that can be used with the get_chart_definition tool and the query_chart tool for further inspection or rendering.
Non-destructive placement — Adds each chart as a new widget without moving or altering any existing widgets on the dashboard.
Limitations
The add_charts_to_dashboard tool has the following limitations:
The user must have edit access to the target dashboard; the tool does not succeed with view-only permissions.
Only charts created through the conversation flow (via the create_chart_from_prompt tool or the refine_chart tool) can be added; manually defined charts are not supported.
Metrics can't be added to a dashboard. If any chart's messageType isn't v2/ChartMessage, the call is rejected and no charts are added.
All charts in a call go to one dashboard; use one call per dashboard.
Each chart is added as a new widget; the tool does not update or replace an existing widget.
If a chart fails, charts already added by the same call stay on the dashboard.
Use Cases
The following items describe use cases for the add_charts_to_dashboard tool:
Publishing an AI-generated chart — After using the create_chart_from_prompt tool to generate a chart from sheet data, use this tool to publish that chart directly onto an operational or executive dashboard.
Multi-chart deployment — When a create_chart_from_prompt response returns several charts, add the ones you want to a dashboard in a single call.
Iterative dashboard building — Combine with the refine_chart tool to iteratively improve a chart before finalizing and publishing it to a dashboard.
Sharing
This section describes Smartsheet MCP server tools for sharing assets with groups and other users.
list_shares
Access scopes: ADMIN_WORKSPACES, SHARE_SHEETS, SHARE_SIGHTS
Toolset: sharing
The list_shares tool retrieves a list of all users and groups with whom a Smartsheet asset has been shared. It returns share details including access levels, user and group information, and share scope, making it useful for understanding who has access to a given asset.
Best Practices
The following items are best practices for using the list_shares tool:
Use the sharing_include parameter to narrow results when you only need direct shares versus inherited workspace shares, as this reduces noise in the response.
When auditing permissions across assets with many collaborators, paginate through all results using last_key before drawing conclusions, since each page returns up to 100 shares.
Combine results from the list_shares tool with the the list_sheets or the browse_workspace tool to build a comprehensive access map across multiple assets.
Basic Parameters
The list_shares tool has the following parameters:
asset_id: The integer ID of the asset whose shares are being listed. This is a required parameter.
asset_type: The type of asset being queried. Accepted values are sheet, report, sight, workspace, collection, and file. This is a required parameter.
last_key: A pagination token used to retrieve the next page of results when an asset has more than 100 shares. Omit the last_key parameter to get the first page of results.
sharing_include: An optional filter for share scope. Use ITEM to return only direct shares, or WORKSPACE to include shares inherited from a parent workspace. The sharing_include parameter defaults to null, meaning no scope filter is applied.
Key Features
The list_shares tool has the following key features:
Multi-asset type support: Works across sheets, reports, sights (dashboards), workspaces, collections, and files, providing a unified way to audit sharing across different Smartsheet content types.
Share scope filtering: The sharing_include parameter lets callers distinguish between shares applied directly to an item (ITEM) and those inherited from a workspace (WORKSPACE).
Access level detail: Each returned share includes the collaborator's access level (e.g., viewer, editor, admin), enabling permission auditing without navigating the Smartsheet UI.
Limitations
The list_shares tool has the following limitations:
Only assets the calling user has permission to view are accessible; shares on assets outside the user's access cannot be retrieved.
Each page returns a maximum of 100 shares, requiring multiple calls with pagination for heavily shared assets.
Use Cases
The following items describe use cases for the list_shares tool:
Permission auditing: Review all users and groups who have access to a specific sheet or workspace to ensure the right people have the right access levels.
Offboarding checks: Verify whether a departing team member still has access to sensitive Smartsheet assets before revoking their access.
Compliance reporting: Generate an access report for a workspace or collection to satisfy internal governance or external compliance requirements.
Access comparison: Compare share lists across multiple assets to identify inconsistencies, such as a report being shared more broadly than its underlying sheet.
Inherited vs. direct share investigation: Use the sharing_include filter to determine whether a user's access to an item is directly granted or inherited from a parent workspace.

Pagination support — Returns results in pages using a lastKey cursor, allowing efficient traversal of large result sets.
Permission flags — Returns permissions on each plan (and each scenario when included) indicating whether the current user can view, edit, delete, share, or apply.
Use Cases
The following items describe use cases for the get_scenario_groups tool:

The get_scenario_group tool has the following parameters:

The get_scenario_group tool has the following key features:

get_scenario_diffs
Toolset: scenario_planning
get_scenario_diffs computes and returns all cell, row, and column differences between a scenario and its source sheets, including blocking and non-blocking conflicts and an aggregate apply-eligibility summary. Use this tool before applying a scenario to explain exactly what would change and whether apply is blocked.
Basic Parameters
The get_scenario_diffs tool has the following parameters:
scenario_id — The taskId of the scenario to compute diffs for. This parameter is required. Obtain it from get_scenario_groups with include_scenarios=true.
Key Features
The get_scenario_diffs tool has the following key features:
Cell-level diffs — Returns every changed cell grouped by row, with scenario and source values, column titles, column types, and column tags.
Row and column additions and deletions — Lists rows and columns that exist only in the scenario, only in the source, or that have been deleted from either side.
Blocking and non-blocking conflicts — Identifies per-sheet conflicts (such as type changes, formula additions, or user-added rows) and flags whether each conflict prevents applying the scenario.
Aggregate apply-eligibility summary — The top-level summary object reports total sheets, conflict counts, cell diff counts, and the can_apply_all_sheets boolean so you can determine apply eligibility at a glance.
Per-sheet diff summaries — Each sheet diff includes a sheet_summary with counts for cell diffs, row and column additions, deletions, and conflicts without requiring traversal of every detail array.
Limitations
The get_scenario_diffs tool has the following limitations:
You must have at least Editor permissions on the workspace and all of the project sheets.
Use Cases
The following items describe use cases for the get_scenario_diffs tool:
Pre-apply review — Inspect all changes a scenario would make to source sheets before committing, so stakeholders can confirm the impact.
Conflict resolution — Surface blocking conflicts and their types to understand what must be resolved before a scenario can be applied.
Change summary reporting — Use summary and per-sheet sheet_summary counts to produce a concise change report across all affected sheets.
Assignee comparison — Compare totalSourceAssignees and totalScenarioAssignees to understand how resource assignments shift between the current plan and the scenario.
get_scenario_capacity_workload
Toolset: scenario_planning
get_scenario_capacity_workload returns capacity (available hours) and workload (assigned hours) for a scenario over a specified date range, broken down by time bucket and grouped by user, discipline, or role. Use it to assess whether a scenario creates over- or under-capacity situations before applying it.
Best Practices
The following items are best practices for using the get_scenario_capacity_workload tool:
Use group_names (preferred over group_ids) to filter results to specific people, disciplines, or roles.
Compute utilization as workload_hours / total_hours; note that placeholder users do not have capacities.
Use instant_type=month for broad planning views (up to a 6-month range) and instant_type=week for detailed scheduling views (up to 26 weeks).
Basic Parameters
The get_scenario_capacity_workload tool has the following parameters:
scenario_id — The taskId of the scenario to query. This parameter is required. Obtain it from get_scenario_groups with include_scenarios=true.
start_date — Start of the date range, inclusive, in YYYY-MM-DD format. This parameter is required.
end_date — End of the date range, inclusive, in YYYY-MM-DD format. This parameter is required.
group_type — Grouping dimension for the results. Accepted values are USER, DISCIPLINE, and RESOURCE_TYPE. The group_type parameter defaults to USER.
instant_type — Time bucket size for the columns. Accepted values are month and week. The instant_type parameter defaults to month.
group_names — Optional list of group display names to filter results. Groups not in this list still appear in the response with 0 hours.
group_ids — Optional list of RM-native group IDs (rmUserId or rmTagId) to filter results. Use group_names instead when display names are available.
filter_roles — Optional list of role names. Only assignments matching these roles contribute non-zero hours.
filter_disciplines — Optional list of discipline names. Only assignments matching these disciplines contribute non-zero hours.
filter_locations — Optional list of location names. Only assignments matching these locations contribute non-zero hours.
filter_assignment_status — Optional assignment-status filter. Accepted values are confirmed for licensed users or placeholder for placeholder resources. For example, confirmed filters on only licensed user capacity and placeholder filters on only placeholder workload hours. Groups with non-matching assignments return 0 hours.
Key Features
The get_scenario_capacity_workload tool has the following key features:
Capacity vs. workload matrix — Returns available total hours and assigned workload hours for each group, keyed by group display name and time bucket label, making it straightforward to calculate utilization.
Flexible grouping — Supports grouping by individual users (USER), discipline (DISCIPLINE), or role (RESOURCE_TYPE) to match different planning perspectives.
Weekly or monthly bucketing — Allows switching between weekly and monthly time buckets to adjust the level of scheduling granularity.
Targeted filtering — Accepts filters by group name, role, discipline, location, and assignment status so that queries can be scoped to exactly the population you care about.
Limitations
The get_scenario_capacity_workload tool has the following limitations:
You must have at least Editor permissions on the workspace and all of the project sheets.
instant_type=month allows at most a 6-month date range; instant_type=week allows at most 26 weeks.
Placeholder users do not have capacity values; only workload hours are returned for them.
Date-range and filter values are validated by the service and may return descriptive errors if invalid.
Use Cases
The following items describe use cases for the get_scenario_capacity_workload tool:
Over-capacity identification — Compare workload hours against available hours per user, discipline or role to find bottlenecks before a scenario is applied.
Resource utilization analysis — Calculate utilization ratios for each team member, discipline or role over a planning horizon to guide staffing decisions.
Scenario comparison — Run this tool against multiple scenarios to compare capacity impact side by side before committing to one.
Filtered team view — Pass group_names, filter_disciplines, or filter_roles to focus the response on a specific team or skill set, reducing noise from unrelated resource groups.
Placeholder vs. confirmed workload — Use filter_assignment_status to separate confirmed assignments from placeholder allocations for more accurate capacity planning.
apply_scenario
Toolset: scenario_planning
apply_scenario applies a scenario's diffs to its source sheets. The operation is accepted asynchronously — a successful response means the apply request was accepted, not that the source sheets have finished updating. (⚠️ destructive)
Best Practices
The following items are best practices for using the apply_scenario tool:
Call get_scenario_diffs first to check for blocking conflicts before calling this tool. The tool returns an error if any source sheet has blocking conflicts.
Basic Parameters
The apply_scenario tool has the following parameters:
scenario_id — The taskId of the scenario whose diffs should be applied to source sheets. This parameter is required. Obtain it from get_scenario_groups with include_scenarios=true.
Key Features
The apply_scenario tool has the following key features:
Asynchronous application — Accepts the apply request immediately and returns a success response while source sheet updates continue in the background.
Diff-based updates — Writes only the changes captured in the scenario's diffs back to the source sheets, leaving unchanged data intact.
Limitations
The apply_scenario tool has the following limitations:
You must have at least Admin permissions on the workspace and all of the project sheets.
Returns an error if the scenario plan already has an applied scenario, or if any source sheet has blocking conflicts. Call get_scenario_diffs first to check for blocking conflicts before calling this tool.
Baseline scenarios cannot be applied; only non-baseline scenarios are eligible.
Requires apply permission on the scenario plan, editor access on all source sheets, and an Enterprise plan with the Scenario Planning feature enabled.
Use Cases
The following items describe use cases for the apply_scenario tool:
Commit a chosen plan — After reviewing scenario diffs and confirming no blocking conflicts exist, apply the preferred scenario to make its changes live across all source sheets.
Finalize resource allocation — Apply a scenario that resolves over-capacity issues or optimizes project timelines once stakeholders have reviewed and approved the plan.
get_shadow_sheet
Toolset: scenario_planning
get_shadow_sheet retrieves a scenario sheet — a scenario-specific copy of a source sheet used by Scenario Planning. The tool returns the sheet structure including columns and rows.
Best Practices
The following items are best practices for using the get_shadow_sheet tool:
Call the get_scenario_groups tool with include_scenarios=true first to obtain the scenario sheet ID from the source_sheet_ids field of a scenario.
Use the exclude parameter to omit cell fields you don't need — such as value and displayValue — to reduce payload size when only column metadata is required.
Call this tool before using the add_shadow_sheet_rows tool, the update_shadow_sheet_rows tool, or the delete_shadow_sheet_rows tool to confirm column IDs and existing row IDs.
Basic Parameters
The get_shadow_sheet tool has the following parameters:
sheet_id — The ID of the scenario sheet to retrieve. This parameter is required. Obtain it from the source_sheet_ids field of a scenario returned by the get_scenario_groups tool with include_scenarios=true.
exclude — An optional list of elements to omit from the response. Accepted values are filteredOutRows, linkInFromCellDetails, linksOutToCellsDetails, nonexistentCells, cellLinks, value, displayValue, image, and imageAltText. The exclude parameter defaults to null.
page — The page number for paginating rows (1-based). The page parameter defaults to 1.
page_size — The number of rows per page. Maximum 500. The page_size parameter defaults to 100.
Key Features
The get_shadow_sheet tool has the following key features:
Full sheet structure — Returns the scenario sheet's columns and rows, providing the complete structure needed to inspect or modify scenario data.
Payload reduction — The exclude parameter omits specific cell fields to reduce response size when only partial cell data is needed.
Limitations
The get_shadow_sheet tool has the following limitations:
The caller must have at least Editor permissions on the workspace and all associated project sheets.
The results don't include a permalink or workspace for the sheet, because the sheets are inaccessible.
Use Cases
The following items describe use cases for the get_shadow_sheet tool:
Pre-edit inspection — Retrieve a scenario sheet's column IDs and existing row IDs before calling the add_shadow_sheet_rows tool, the update_shadow_sheet_rows tool, or the delete_shadow_sheet_rows tool.
Scenario state review — Inspect the current data in a scenario sheet to understand how a scenario differs from its source sheet before applying it.
get_shadow_sheet_row
Toolset: scenario_planning
get_shadow_sheet_row retrieves a single row from a scenario sheet by its row ID in a Scenario Planning scenario. The tool returns the full row data including cell values.
Best Practices
The following items are best practices for using the get_shadow_sheet_row tool:
Call the get_shadow_sheet tool first to list rows and obtain valid row IDs before retrieving a specific row.
Use this tool to confirm current cell values before performing an update with the update_shadow_sheet_rows tool.
Basic Parameters
The get_shadow_sheet_row tool has the following parameters:
sheet_id — The ID of the scenario sheet containing the row. This parameter is required. Obtain it from the source_sheet_ids field of a scenario returned by the get_scenario_groups tool with include_scenarios=true.
row_id — The ID of the row to retrieve. This parameter is required. Obtain it from the rows returned by the get_shadow_sheet tool.
Key Features
The get_shadow_sheet_row tool has the following key features:
Single-row retrieval — Returns complete data for one row, including all cell values, without fetching the full scenario sheet.
Targeted inspection — Efficiently reads a specific row by ID, useful for confirming current values before an update.
Limitations
The get_shadow_sheet_row tool has the following limitations:
Only one row is returned per call.
The sheet_id must identify a scenario sheet, not a regular sheet.
Requires at least Editor permissions on the workspace and all associated project sheets.
Use Cases
The following items describe use cases for the get_shadow_sheet_row tool:
Pre-update verification — Confirm a row's current cell values before modifying it with the update_shadow_sheet_rows tool.
Targeted data inspection — Retrieve a single row's data without loading the full scenario sheet, reducing response size.
add_shadow_sheet_rows
Toolset: scenario_planning
add_shadow_sheet_rows adds one or more rows to a scenario sheet in a Scenario Planning scenario. Each row can specify where it is inserted using location specifiers. The tool returns the newly created rows.
Best Practices
The following items are best practices for using the add_shadow_sheet_rows tool:
Call the get_shadow_sheet tool first to confirm the sheet structure and obtain column IDs.
Ensure every row in the rows array specifies the same positioning attribute or an acceptable combination (toBottom, toTop, parentId, siblingId, or above). Split rows with different locations into separate calls.
Use parentId to insert a row as a child of an existing row. Combine with toBottom=true to place it as the last child.
Basic Parameters
The add_shadow_sheet_rows tool has the following parameters:
sheet_id — The ID of the scenario sheet to add rows to. This parameter is required. Obtain it from the source_sheet_ids field of a scenario returned by the get_scenario_groups tool with include_scenarios=true.
rows — A list of one or more row objects to add. This parameter is required. Each row object can contain the following fields:
cells — An optional array of cell objects. Each cell requires a columnId and either a value or a formula.
toBottom, toTop — Booleans to position the row at the bottom or top of the sheet.
parentId — The row ID of the parent row to nest this row under as a child.
siblingId — The row ID to place this row next to at the same indentation level.
above — When true, positions the row above the specified siblingId.
indent, outdent — Number of levels to adjust the row's hierarchy. Must be used alone, without other location specifiers.
expanded, locked, format — Optional row properties.
Key Features
The add_shadow_sheet_rows tool has the following key features:
Flexible positioning — Supports toTop, toBottom, parentId, siblingId, and above location specifiers to insert rows at any position in the scenario sheet.
Hierarchical placement — Use parentId and indent to create parent-child row relationships and multi-level hierarchies within the scenario.
Batch insertion — Adds up to 500 rows in a single call for efficient scenario population.
Limitations
The add_shadow_sheet_rows tool has the following limitations:
Maximum 500 rows per call.
Does not support rows with image cells.
The sheet_id must identify a scenario sheet, not a regular sheet.
Every row in the rows array must specify the same positioning attribute or a compatible combination; rows with different locations require separate calls.
Use Cases
The following items describe use cases for the add_shadow_sheet_rows tool:
Scenario population — Add new task rows to a scenario sheet to model additional work items in a "what-if" scenario before comparing it to the baseline.
Hierarchical structure — Insert child rows under existing parent rows to add phases or subtasks within a scenario's project plan.
Bulk row insertion — Add up to 500 rows in a single call to efficiently build out a scenario's scenario sheet.
update_shadow_sheet_rows
Toolset: scenario_planning
The update_shadow_sheet_rows tool modifies one or more existing rows in a scenario sheet in a Scenario Planning scenario. Each row object must include a row ID identifying which row to update. The tool returns the updated rows.
(⚠️ destructive, irreversible)
Best Practices
The following items are best practices for using the update_shadow_sheet_rows tool:
Call the get_shadow_sheet tool first to retrieve row IDs, then call the get_shadow_sheet_row tool to confirm current cell values before updating.
Include only the fields you want to change. Unspecified fields are left unchanged.
Review the results for errors before calling the apply_scenario tool.
Basic Parameters
The update_shadow_sheet_rows tool has the following parameters:
sheet_id — The ID of the scenario sheet containing the rows to update. This parameter is required. Obtain it from the source_sheet_ids field of a scenario returned by the get_scenario_groups tool with include_scenarios=true.
rows — A list of one or more row objects to update. This parameter is required. Each row object must include the following fields:
id — The ID of the row to update. This field is required.
cells — An optional array of cell objects. Each cell requires a columnId and either a value or a formula.
toBottom, toTop, parentId, siblingId, above, indent, outdent — Optional location specifiers to move the row simultaneously with updating its data.
expanded, locked, format — Optional row properties.
Key Features
The update_shadow_sheet_rows tool has the following key features:
Partial updates — Only modifies the fields you specify; all other row data remains unchanged.
Combined data and position update — Updates cell values and repositions a row in a single operation using location specifiers.
Batch updates — Modifies up to 500 rows in a single call.
Limitations
The update_shadow_sheet_rows tool has the following limitations:
Maximum 500 rows per call.
Updates are permanent within the scenario and cannot be automatically undone.
The sheet_id must identify a scenario sheet, not a regular sheet.
Each row object must include an id field; rows cannot be identified by position or content.
Use Cases
The following items describe use cases for the update_shadow_sheet_rows tool:
Scenario adjustment — Modify task dates, assignments, or statuses in a scenario sheet to model a different resource allocation or timeline before comparing it to the baseline.
Bulk cell updates — Change values across multiple rows in a single call to efficiently update a scenario's project data.
Row repositioning — Move rows to different positions or hierarchy levels within the scenario sheet while simultaneously updating their cell values.
delete_shadow_sheet_rows
Toolset: scenario_planning
The delete_shadow_sheet_rows tool permanently removes one or more rows from a scenario sheet in a Scenario Planning scenario by row ID. The response contains the IDs of all deleted rows, including child rows of any specified parent rows.
(⚠️ destructive, irreversible)
Best Practices
The following items are best practices for using the delete_shadow_sheet_rows tool:
Call the get_shadow_sheet tool first to retrieve rows and confirm their IDs before deleting.
Verify the row hierarchy before deleting parent rows, as deleting a parent row also deletes all its child rows.
Basic Parameters
The delete_shadow_sheet_rows tool has the following parameters:
sheet_id — The ID of the scenario sheet to delete rows from. This parameter is required. Obtain it from the source_sheet_ids field of a scenario returned by the get_scenario_groups tool with include_scenarios=true.
row_ids — An array of one or more row IDs to delete. This parameter is required.
Key Features
The delete_shadow_sheet_rows tool has the following key features:
Cascading deletion — Deleting a parent row automatically deletes all its child rows. The response lists every deleted row ID, including children.
Batch deletion — Removes multiple rows in a single call.
Limitations
The delete_shadow_sheet_rows tool has the following limitations:
Deletion is permanent within the scenario and cannot be automatically undone.
The sheet_id must identify a scenario sheet, not a regular sheet.
Requires at least Editor permissions on the workspace and all associated project sheets.
Use Cases
The following items describe use cases for the delete_shadow_sheet_rows tool:
Scenario simplification — Remove tasks or milestones from a scenario sheet that are not relevant to a particular "what-if" scenario being modeled.
Hierarchy pruning — Delete parent rows along with all their children to eliminate entire work packages from a scenario in a single operation.
Scenario cleanup — Remove incorrectly added rows from a scenario sheet before using the get_scenario_diffs tool or the apply_scenario tool.
User plans
The following sections describe Smartsheet MCP server tools for managing users plans and seats.
get_plan_id
Access scopes: Not applicable
Toolset: users
Important: The get_plan_id is available to system admins only.
The get_plan_id tool retrieves the list of plans that the authenticated user is a member of. It is primarily used to discover a planId when it is required by other plan-based operations, such as retrieving seat requests or managing plan members. The user's identity is resolved automatically from the authenticated session, so no user ID input is required.
Best Practices
The following items are best practices for using the get_plan_id tool:
Call this tool first whenever a plan-based tool requires a planId and the user has not provided one.
If only one plan is returned, use that planId directly without asking the user.
If multiple plans are returned, present the list to the user using plan_name to identify each plan, with seat_type and is_internal as additional context, and ask them to confirm which planId to use.
If last_key is present in the response, fetch the next page before presenting the full list to the user.
Basic Parameters
The get_plan_id tool has the following parameters:
last_key — an opaque pagination token for fetching the next page of results. The last_key parameter defaults to an empty string.
max_items — the maximum number of items to return per page (1–100). The max_items parameter defaults to 100.
Key Features
The get_plan_id tool has the following key features:
Session-based identity resolution: The authenticated user's ID is resolved automatically from the session — no user ID input is required.
Pagination support: Supports keyset pagination via last_key to iterate through plans when the user belongs to many.
Plan context fields: Returns plan_name, seat_type, and is_internal to help identify and select the correct plan when multiple are present.
Limitations
The get_plan_id tool has the following limitations:
Returns plan memberships for the authenticated user only — cannot look up plans for other users.
plan_name may be absent for plans whose organization cannot be resolved; fall back to the raw planId when presenting such a plan.
Admin status is not surfaced by this endpoint — it exists at the org layer and cannot be inferred from plan membership data.
Use Cases
The following items describe use cases for the get_plan_id tool:
Plan ID discovery: Resolves the planId required before calling tools such as the get_seat_requests tool or the get_seat_usage tool.
Multi-plan selection: Presents users who belong to multiple plans with a labeled list so they can confirm which plan to target.
get_seat_usage
Access scopes: ADMIN_USERS
Toolset: users
The get_seat_usage tool retrieves per-user seat usage detail and activity scores for a plan as a flat, paginated list. Plan administrators use it to review who holds seats, how users are billed, and how active each user is.
This tool is unavailable for the Microsoft 365 Copilot Connector (the Copilot Studio connector for Copilot Chat)
Best Practices
The following items are best practices for using the get_seat_usage tool:
Paginate through all pages by passing the last_key from each previous response into the next call until no last_key is returned.
Use the activity_window parameter to match the lookback period to your review cycle — longer windows produce more stable scores for infrequent but legitimate users.
Combine min_activity_score/max_activity_score with billing_states to identify paid seats held by inactive users before making licensing decisions.
Basic Parameters
The get_seat_usage tool has the following parameters:
plan_id — the ID of the plan to query. Required.
seat_types — filters results to one or more seat types: MEMBER, PROVISIONAL_MEMBER, GUEST, or CONTRIBUTOR.
billing_states — filters results to one or more billing states: PAID, CONVERT_THIS_CYCLE, CONVERT_NEXT_CYCLE, or FREE.
departments — filters results to one or more department names.
user_ids — filters results to one or more specific user IDs.
min_activity_score — lower bound (inclusive) on the activity score filter (0–100).
max_activity_score — upper bound (inclusive) on the activity score filter (0–100).
activity_window — the lookback period used to compute each user's activity score. The activity_window parameter defaults to NINETY_DAYS. Other values are ONE_HUNDRED_EIGHTY_DAYS, TWO_HUNDRED_SEVENTY_DAYS, and THREE_HUNDRED_SIXTY_FIVE_DAYS.
max_items — the maximum number of users returned per page. The max_items parameter defaults to 25.
last_key — the pagination token used to fetch the next page of results. The last_key parameter defaults to an empty string (first page).
sort_order — the sort direction (ASC or DESC) applied to the activity score column. The sort_order parameter defaults to DESC.
Key Features
The get_seat_usage tool has the following key features:
Activity scoring — computes a 0–100 activity score per user based on the configured activity_window, along with component-level detail supporting nuanced engagement analysis.
Flexible filtering — supports simultaneous filtering by seat type, billing state, department, user ID, and activity score range.
Limitations
The get_seat_usage tool has the following limitations:
The caller must be an administrator of the plan.
The maximum page size is 100 users per page; larger result sets require multiple paginated calls.
Use Cases
The following items describe use cases for the get_seat_usage tool:
License reclamation — identify paid seats with low activity scores to reclaim unused licenses and reduce costs.
Inactive user review — filter by min_activity_score/max_activity_score to generate a list of users who have not engaged with the plan recently.
Billing audit — combine billing_states and seat_types filters to audit which users are in a conversion or paid state ahead of a billing cycle.
Department-level reporting — filter by departments to produce per-department seat usage and activity summaries for team managers.
get_license_inventory
Access scopes: ADMIN_USERS
Toolset: users
get_license_inventory retrieves a point-in-time license usage snapshot for a Smartsheet plan. System administrators use it to check available licenses, track usage against plan limits, and monitor reconciliation period activity.
This tool is unavailable for the Microsoft 365 Copilot Connector (the Copilot Studio connector for Copilot Chat)
Best Practices
The following items are best practices for using the get_license_inventory tool:
Use the get_plan_id tool to look up a plan ID if you don't already have one.
Pass period=RECON when you need usage counts scoped to the current reconciliation window rather than the full plan period.
Basic Parameters
The get_license_inventory tool has the following parameters:
plan_id — ID of the plan to retrieve license inventory for. This parameter is required.
period — Reporting period for the counts: ALL or RECON. This parameter is optional. The period parameter defaults to ALL, which reports counts across the full plan period.
Key Features
The get_license_inventory tool has the following key features:
License counts and limits. Reports the number of member licenses in use and the total allowed under the plan.
Provisional and guest/contributor counts. Includes counts for provisional members and guest or contributor users separately from licensed members.
Pending purchase tracking. Reports how many additional licenses still need to be purchased to cover current membership.
Reconciliation window scoping. Supports a RECON period option to isolate counts to the current reconciliation window.
Date visibility. Returns plan usage period dates and the current reconciliation period dates alongside the counts.
Limitations
The get_license_inventory tool has the following limitations:
Requires the caller to be an administrator of the plan.
Use Cases
The following items describe use cases for the get_license_inventory tool:
Available license check. Answer "how many licenses are left on my plan?" before provisioning new members.
Reconciliation review. Determine usage within the current reconciliation window to anticipate billing adjustments before the period closes.
Capacity planning. Compare current license consumption against plan limits to decide whether to purchase additional seats.
Pending purchase audit. Identify how many licenses need to be purchased to bring the plan into compliance with current membership counts.
